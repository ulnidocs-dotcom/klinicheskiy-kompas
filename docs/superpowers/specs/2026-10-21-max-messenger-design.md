# Клинический компас в мессенджере MAX и перенос данных на веб-платформу — дизайн

Дата: 2026-10-21. Статус: утверждён пользователем, ожидает ревью текста.
Основание: запрос «адаптировать бота под мессенджер MAX с дальнейшей пересадкой информации на сайт или веб-платформу».

## 1. Цель и рамки

Пациентская часть прототипа (сейчас — Telegram Mini App) должна работать как мини-приложение MAX. Данные пациента должны попадать на веб-платформу в двух сценариях (оба выбраны пользователем):

1. **MAX → кабинет врача.** Пациент отмечает самочувствие, приём препарата, шкалы в MAX. Отметки сразу видны врачу и психологу на сайте.
2. **Переезд пациента на сайт.** Пациент может перейти из MAX в веб-кабинет без потери истории; MAX после этого не обязателен.

**Уровень:** демо-прототип на мок-данных плюс готовый контракт для сервера (решение пользователя). Настоящего сервера, бота и базы в этой работе нет.

**Вне рамок:** серверная реализация, хостинг, регистрация организации и мини-приложения на платформе MAX (это делает владелец проекта: подключение доступно юрлицам, ИП и самозанятым — резидентам РФ), отдельный веб-кабинет пациента как новый набор экранов (веб-канал использует те же страницы `patient/`).

## 2. Факты о платформе MAX (проверено по dev.max.ru, 2026-10-21)

| Что | Как в MAX | Источник |

| Данные запуска | `WebApp.initData` (строка в URL-кодировке, для сервера), `initDataUnsafe` (только для интерфейса), `platform`, `version` | там же |
| Кнопка «Назад» | `WebApp.BackButton.show/hide/onClick/offClick` | там же |
| Прочее | `HapticFeedback`, `openLink`, `openMaxLink`, `enableClosingConfirmation`/`disableClosingConfirmation`, `DeviceStorage`, `SecureStorage` (до 10 ключей, не работают в веб-клиенте MAX), `downloadFile`, `shareContent` | там же |

## 3. Архитектура

```
 MAX (мини-приложение) ─┐
 Telegram (Mini App) ───┼─> KK.host (адаптер платформы) ─> страницы patient/* ─> KK.sync (очередь) ─> транспорт
 Браузер (веб-канал) ───┘                                                                         ├─ local: общий localStorage (демо)
                                                                                                   └─ http: контракт /v1 (сервер, вне рамок)
 Кабинеты врача и психолога (сайт) <──────────────────── те же данные ─────────────────────────────┘
```

Интерфейс пациента один для всех каналов. Отличия платформ спрятаны в `KK.host`, отправка данных — в `KK.sync`. Кабинеты врача и психолога не знают, из какого канала пришла отметка; канал хранится в событии как поле `channel` для журнала.

### 3.1 Адаптер платформы `assets/host.js` (заменяет `assets/tg.js`)

Определение платформы, по порядку:
1. `window.WebApp` есть и `initData` непустая → `max`;
2. `window.Telegram.WebApp` есть, `platform` не `unknown` → `telegram`;
3. иначе → `web`.

Интерфейс `KK.host` (одинаковый для всех платформ, на `web` методы безопасно ничего не делают):

| Метод / поле | max | telegram | web |
|---|---|---|---|
| `platform` | `'max'` | `'telegram'` | `'web'` |
| `inside` | `true` | `true` | `false` |
| `init()` | применить сохранённую тему | `ready()`, `expand()`, тема из `colorScheme` | — |
| `backButton(fn)` | `BackButton.show/onClick` | `BackButton.show/onClick` | — (на странице своя ссылка «Назад») |
| `haptic()` | `HapticFeedback` | `HapticFeedback.selectionChanged` | — |
| `openLink(url)` | `openLink` | `openLink` | `window.open` |
| `startParam()` | `initDataUnsafe.start_param` | `initDataUnsafe.start_param` | `?startapp=` из URL (для демо) |
| `initData()` | `WebApp.initData` | `Telegram.WebApp.initData` | `''` |
| `guardClose(on)` | `enable/disableClosingConfirmation` | `enable/disableClosingConfirmation` | `beforeunload` |
| `draft` (черновики) | `DeviceStorage`, при недоступности — `localStorage` | `localStorage` | `localStorage` |
| `setTheme(t)` | сохранить в `kk:theme:patient` | то же | то же |

Решения:
- **Главной кнопки у MAX нет в документации** — оставляем кнопки на странице во всех каналах (`mainButton` из `tg.js` не переносим, она нигде не вызывается).
- **Темы у MAX нет в документации** — тема берётся из выбора пациента, иначе из `prefers-color-scheme`, как в браузере.
- `KK.tg` остаётся псевдонимом `KK.host` на переходный период, чтобы не править все вызовы одним коммитом; вызовы в `patient.js`, `today.js`, `scale.js`, `intake.js`, `theme.js` переводятся на `KK.host`, затем псевдоним удаляется.
- `guardClose` включается на время анкеты первичного приёма и шкал, чтобы случайный свайп не терял ответы.
- Скрипты платформ подключаются в `patient/*.html` оба; каждый безопасен вне своей платформы. Сборка ссылки-демо (`tools/build-artifact.js`) вырезает и скрипт Telegram, и скрипт MAX.

### 3.2 Пациент, каналы и привязка

Модель (общая для демо и сервера):
- **Пациент** — внутренний `patientId`; вся история (события, шкалы, план, согласия) хранится по нему.
- **Привязка канала** — `{ channel: 'max' | 'telegram' | 'web', externalId, linkedAt, revokedAt }`. Для `max`/`telegram` `externalId` — `user.id` из проверенной `initData`; для `web` — логин веб-кабинета.
- У пациента может быть несколько активных привязок; отвязка канала не удаляет историю.

**Первый вход из MAX.** Врач выдаёт приглашение. В демо — код `KMP-xxxx` (как сейчас). В контракте — ссылка `https://max.ru/<bot>?startapp=inv_<токен>`, где токен одноразовый, живёт 72 часа и не содержит персональных данных. Мини-приложение читает `startParam()`, сервер гасит токен и создаёт привязку `max`. Без приглашения пациент видит онбординг с вводом кода (как сейчас).

**Переезд на сайт.** В профиле пациента пункт «Открыть на сайте»:
1. Создаётся одноразовый код привязки (6 цифр, живёт 10 минут, одна попытка гашения, в демо хранится в `localStorage`).
2. Пациенту показывается адрес веб-кабинета и код; ссылка открывается через `KK.host.openLink`.
3. На сайте пациент вводит код → создаётся привязка `web` к тому же `patientId` → вся история на месте.
4. В профиле видно, какие каналы подключены, и можно отключить канал.

В демо веб-кабинет пациента — те же страницы `patient/` в обычном браузере (`KK.host.platform === 'web'`).

### 3.3 Синхронизация `assets/sync.js`

Каждое действие пациента (отметка самочувствия, приём дозы, шкала, нежелательное явление, SOS, сообщение) проходит через `KK.sync.submit(patientId, type, payload)`:
- событию присваивается `clientId` (ключ идемпотентности) и `channel = KK.host.platform`;
- событие кладётся в очередь со статусом `pending` и сразу применяется локально (пациент видит результат без ожидания);
- транспорт отправляет очередь пакетами; ответ сервера `accepted` или `duplicate` переводит событие в `sent`; ошибка сети оставляет `pending` и повторяет с паузой 2, 4, 8 … до 60 секунд;
- сервер — источник истины; повтор с тем же `clientId` не создаёт второе событие.

Транспорты:
- `local` (демо): пишет в существующий `KK.store` — врач видит данные в соседней вкладке через событие `storage`, как сейчас; ответ всегда `accepted`;
- `http` (контракт): `POST /v1/patients/{id}/events:batch`. В демо не включается.

**Исключение: SOS и ответы, поднимающие критический алерт, не ждут очереди** — отправляются немедленно; при отсутствии связи пациенту показывается «Сообщение не отправлено. Если опасно сейчас — звоните 112» (связь со спеком безопасности: пациенту не обещается доставка, которой нет).

Пациент видит статус одной строкой: «Сохранено» или «Сохранено на телефоне, отправится при появлении связи».

### 3.4 Бот в чате MAX (только контракт)

Бот нужен для напоминаний; основная работа — в мини-приложении.

| Сообщение | Когда | Кнопки |
|---|---|---|
| «Время принять препарат» | по плану приёма (утро/вечер) | `callback` «Принял» → событие `dose` через сервер; `open_app` «Открыть дневник» |
| «Как вы сегодня? Это займёт минуту» | раз в день в выбранное пациентом время | `open_app` «Отметить» |
| «Врач ответил вам» | новое сообщение врача | `open_app` «Открыть переписку» |

Правила текстов: без названия препарата, диагноза и баллов — уведомление видно на заблокированном экране. Кнопка «Принял» в чате создаёт то же событие, что и кнопка в мини-приложении, с `channel: 'max-chat'`. Пациент может отключить напоминания в профиле.

### 3.5 Пакет переноса `kompas-bundle v1`

JSON-документ для переезда между платформами и для права пациента на получение своих данных (152-ФЗ):

```json
{
  "format": "kompas-bundle", "version": 1, "exportedAt": "2026-10-21T10:00:00Z",
  "rulesVersion": "2026.10.1",
  "patient": { "id": "p_anna", "name": "…", "age": 34, "sex": "f", "diagnoses": [], "meds": [], "labs": {}, "plan": {} },
  "channels": [{ "channel": "max", "linkedAt": "…" }],
  "consents": [{ "kind": "data_processing", "at": "…", "version": "1" }],
  "events": [{ "id": "ev_…", "clientId": "…", "type": "checkin", "at": "…", "recordedAt": "…", "channel": "max", "payload": {} }],
  "decisions": [{ "kind": "routing", "at": "…", "by": "doctor", "ruleVersion": "…" }]
}
```

- В пакете нет `externalId` каналов, токенов, кодов привязки и служебных отпечатков алертов.
- Алерты не переносятся: на новой платформе они пересчитываются правилами из событий.
- У пациента — «Скачать мои данные» в профиле (в MAX — `downloadFile` по ссылке с сервера; в демо и браузере — обычное скачивание файла; если `downloadFile` не принимает локальный файл, показывается текст пакета с кнопкой «Скопировать»). У врача — «Экспорт» в карточке пациента.
- Импорт: `KK.bundle.import(json)` проверяет формат и версию, отклоняет неизвестную версию, не создаёт дублей событий (по `id`/`clientId`).

### 3.6 API-контракт

Файл `docs/api/openapi.yaml` (OpenAPI 3.1) и краткое описание `docs/api/README.md`.

| Метод | Назначение |
|---|---|
| `POST /v1/auth/max` | `{ initData }` → проверка по §2 → сессия пациента (`401` при неверной подписи или `auth_date` старше часа) |
| `POST /v1/auth/telegram` | то же для Telegram |
| `POST /v1/invites/{token}:redeem` | погасить приглашение врача, создать привязку канала |
| `POST /v1/link-codes` / `POST /v1/link-codes:redeem` | создать и погасить код переезда на сайт |
| `GET /v1/patients/{id}/channels`, `DELETE …/channels/{channel}` | список и отключение каналов |
| `POST /v1/patients/{id}/events:batch` | пакет событий с `clientId`; ответ по каждому: `accepted` / `duplicate` / `rejected` с причиной |
| `GET /v1/patients/{id}/events?since=` | события после отметки времени (кабинеты, второй канал пациента) |
| `GET /v1/patients/{id}/export` | `kompas-bundle v1` |
| `POST /v1/max/webhook` | обновления бота MAX (`message_callback` от кнопки «Принял», `bot_started`) |

Доступ: пациент видит только себя; врач и психолог — пациентов по связи «специалист — пациент» (`care_relations`, как обсуждалось ранее). Токен бота хранится только на сервере.

Эталонная проверка `initData` — `tools/max-initdata.js` (Node, без зависимостей, `crypto.createHmac`), чтобы серверная реализация могла сверить результат на тех же тестовых векторах.

## 4. Обработка ошибок

- Нет связи → событие остаётся в очереди, пациент видит «отправится при появлении связи»; при повторном открытии мини-приложения очередь отправляется заново.
- Сервер ответил `rejected` → событие помечается, пациенту — «Не удалось сохранить, попробуйте ещё раз»; ответы остаются на экране (как сейчас при ошибке стора).
- `DeviceStorage` недоступен (веб-клиент MAX) → черновики в `localStorage`.
- `initData` пустая или неверная → вход только по коду приглашения; никаких данных пациента до привязки.
- Код переезда истёк или уже погашен → понятное сообщение и кнопка «Получить новый код».
- Неизвестная версия пакета при импорте → отказ без частичного импорта.

## 5. Проверка

Тесты (Node, `node --test`):
- `host`: определение платформы на подставных `window.WebApp` и `window.Telegram.WebApp`; на `web` все методы безопасны; `startParam` из каждого источника.
- `max-initdata`: верная подпись проходит; изменённое поле, чужой токен, `auth_date` старше часа — отклоняются; `hash` не входит в строку проверки; сортировка по ключу.
- `sync`: повтор с тем же `clientId` не дублирует событие; очередь переживает «перезагрузку»; SOS идёт мимо очереди.
- `bundle`: экспорт → импорт даёт те же события и план; секретов нет в пакете; неизвестная версия отклоняется.
- Привязка: код живёт 10 минут и гасится один раз; после переезда история та же.
- `build`: ссылка-демо не содержит скриптов `telegram.org` и `st.max.ru`.

В браузере: пациент в режиме `web` и с подставным `window.WebApp` (имитация MAX): кнопка «Назад», черновики, «Открыть на сайте», «Скачать мои данные»; врач видит отметки с пометкой канала в ленте событий; адаптивность на 320/375/768.

Проверка в настоящем MAX — после того как владелец разместит прототип по HTTPS и подключит мини-приложение в кабинете организации.

## 6. Открытые вопросы

- Типы кнопок (`open_app`, `callback`) и событий бота (`message_callback`, `bot_started`) сверить с официальной документацией Bot API MAX при реализации сервера.
- Поддержка `start_param` подтверждена только страницей обзора мини-приложений; на странице валидации поле не показано — проверить на реальном запуске.
- Хостинг демо для MAX (GitHub Pages, Yandex Cloud или VK Cloud) и организация, на которую подключается мини-приложение, — решение владельца.
